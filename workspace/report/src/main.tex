\begin{abstract}
This report presents the design and implementation of a dual-core machine learning accelerator tailored for attention mechanisms, a core component of modern transformer models. The architecture features an asynchronous clocking scheme with a dual-core setup to parallelize the matrix multiplication and normalization phases. Furthermore, a hardware-optimized sparsity-aware Softmax (SFP) engine is introduced, utilizing row-energy accumulation and cross-core sum exchange to execute accurate fixed-point normalization. We also outline a comprehensive step-by-step verification methodology that spans from single-core RTL design to full-chip hierarchical physical design (PnR) using a 65nm process. Architectural optimizations, such as repipelining the divider and adder tree, dramatically reduced the critical path delay from over 24\,ns to under 1\,ns, achieving zero timing violations. Finally, our design achieves fully functional gate-level simulations and successful tape-out-ready physical layouts.
\end{abstract}

\section{Introduction}
Attention mechanisms have revolutionized natural language processing and computer vision by enabling models to dynamically weigh the importance of different input elements. At the core of the attention mechanism is the computation of attention scores, which determines how much focus a query should place on various keys. This is mathematically expressed as multiplying a Query matrix (Q) with a transposed Key matrix (K) to obtain raw attention scores. These raw scores are then normalized using a Softmax function, converting them into a valid probability distribution where all weights sum to one. Finally, the normalized attention weights are multiplied by a Value matrix (V) to produce the final output context vectors.

However, the associated matrix multiplication (MatMul) and Softmax normalization operations pose significant computational and memory bandwidth challenges. The Softmax function, in particular, requires global awareness of the entire row (or sequence) to compute the normalizing sum, creating a bottleneck in deeply pipelined hardware. To address these bottlenecks, this project proposes a dual-core hardware accelerator designed specifically for the attention mechanism.

The proposed design leverages two independent cores communicating via asynchronous FIFOs, allowing flexible scheduling and increased throughput. To efficiently handle the Softmax operation, we developed a Sparsity-Aware Softmax (SFP) engine that skips redundant computations for zero or near-zero data, thereby saving power and cycles.

Due to the immense complexity of the dual-core asynchronous design, a rigorous, step-by-step implementation and verification strategy was adopted. This incremental approach, ranging from basic single-core synthesis to full-chip hierarchical place-and-route (PnR), ensured functional correctness at every stage. This report details both the theoretical architecture of the accelerator and the practical milestones achieved during its physical implementation.

\section{Proposed Architecture}

\subsection{Dual-Core System \& Asynchronous Clocking}
To maximize throughput, the accelerator is partitioned into two distinct processing cores (Core 0 and Core 1). Each core operates in its own clock domain (\texttt{clk0} and \texttt{clk1}) to simulate realistic system-on-chip (SoC) environments where different functional blocks might run at different frequencies. Data and control signals are securely transferred between the two clock domains using asynchronous FIFOs (Async FIFO). This cross-domain communication (CDC) ensures that matrix chunks processed by one core can be synchronized with the other core without meta-stability issues, particularly during the global sum accumulation required for Softmax normalization.

\subsection{Core Controller \& Data Flow}
Each core features an independent controller and a memory map (\texttt{reg\_map}) to handle top-level configurations. The controller manages the data flow between the Query Memory (QMEM), Key Memory (KMEM), the MAC array, and the SFP engine based on the defined operation mode (\texttt{op\_mode}):
\begin{itemize}
    \item \textbf{Mode 1 (MatMul Only):} The core multiplies data from QMEM and KMEM using the MAC array, and directly stores the result into the Partial Sum Memory (PMEM).
    \item \textbf{Mode 0 (MatMul + Normalization):} Data from QMEM and KMEM are multiplied, and the resulting partial sums are fed into the SFP engine. The normalized outputs are then written back to either PMEM or KMEM, dictated by \texttt{sfp\_write\_to\_pmem} and \texttt{sfp\_write\_to\_kmem} flags.
\end{itemize}
The controller automatically generates status flags (e.g., \texttt{qmem\_free}) to notify upper-level modules when memory banks are available for new data, enabling efficient cycle-saving data prefetching.

\subsection{Sparsity-Aware Softmax (SFP) Engine}
The SFP row block is responsible for normalizing one row of the MAC array outputs. The normalization process is divided into two pipelined phases:
\begin{enumerate}
    \item \textbf{Accumulation (acc):} When \texttt{acc\_start} is pulsed, the engine computes the row energy $S_{i} = \sum_{j} |sfp\_in[j]|$ using an adder tree. The sum is temporarily stored in an internal FIFO, and \texttt{acc\_done} is asserted upon completion.
    \item \textbf{Division (div):} During the division phase, triggered by \texttt{div\_start} (which is gated by a \texttt{div\_busy} signal to prevent overlapping operations), the engine retrieves the local sum from the FIFO and adds it to the sum from the other core (\texttt{sum\_in}). It then computes the normalized output:
    \begin{equation}
        sfp\_div\_out[c] = \text{trunc}\left(\frac{|sfp\_in[c]| \ll out\_shift}{S_{local} + sum\_in}\right)
    \end{equation}
    Upon finishing the division, a \texttt{div\_done} pulse is generated to indicate that the normalized results are valid.
\end{enumerate}
To further optimize performance, a sparsity gating mechanism is implemented. If the computed row energy $S_{i}$ is strictly less than a configurable \texttt{SFP\_THRESHOLD}, the engine bypasses the division and outputs all zeros. This effectively filters out negligible attention scores, conserving dynamic power.

\section{Design Methodology and Verification Infrastructure}
To facilitate rapid development and reliable testing of the dual-core design, a robust Makefile-driven flow and shell-based verification infrastructure were established.

\subsection{Makefile Management}
A centralized Makefile provides unified commands for behavioral simulation, synthesis, and gate-level simulation (GLS) across various design targets (e.g., \texttt{fullchip}, \texttt{core}, \texttt{mac}, \texttt{sfp\_row}). By standardizing the build system, team members could seamlessly run target-specific tests using commands such as \texttt{make sim TARGET=core} or \texttt{make syn TARGET=mac}, significantly improving development efficiency and avoiding configuration errors.

\subsection{Shell-Based Verification and Automated Parsing}
Synthesis quality of results (QoR) and timing closure were continuously tracked using a custom shell-based parser (\texttt{parse\_reports.sh}). Integrated into the Makefile as the \texttt{make parse} target, this tool automatically scans Design Compiler output reports to extract and summarize critical metrics, including total cell area, dynamic power, leakage power, and Worst Negative Slack (WNS). This automated reporting mechanism proved essential during the RTL optimization phase (Step 5), allowing the team to quickly evaluate the impact of repipelining the SFP block on the overall critical path.

\subsection{Step 2: Output Normalization}
The single-core MAC array was integrated with the SFP (Softmax with Fixed-Point) row block. The SFP block normalizes the partial sums row by row in two phases: \textit{accumulation} and \textit{division}. 

During the \textbf{accumulation (acc)} phase, the block calculates the row energy by summing the absolute values of the incoming partial sums from the MAC array ($S_i = \sum |sfp\_in[j]|$). 

In the \textbf{division (div)} phase, each absolute partial sum is divided by the global row sum to produce the normalized output. To support multi-core scaling, the global sum combines the local core's sum ($S_i$) with the sum from the other core ($sum\_in$). 

Since the theoretical output of the normalization falls within the range $[0, 1]$, integer division would yield zero for almost all values. To address this, a fixed-point scaling mechanism is introduced using the \texttt{out\_shift} parameter. The numerator is logically left-shifted by \texttt{out\_shift} bits before division: 
\[ sfp\_div\_out[c] = \text{truncate}\left(\frac{|sfp\_in[c]| \ll out\_shift}{S_i + sum\_in}\right) \]
This shift defines the fractional precision of the output. For example, a default \texttt{out\_shift = 7} allocates 7 bits for the fractional part, mapping the $[0, 1]$ range to $[0, 128]$ in the 8-bit output. Behavioral simulations verified that these calculations correctly normalize the partial sums. Figure~\ref{fig:s2_wave} shows the simulation waveform demonstrating the functional correctness of the Step 2 design, with the output matching the expected normalized values.

\subsection{Step 5: Alphas (Architecture Optimization)}
Initial synthesis results highlighted a massive timing violation (Worst Negative Slack $\approx$ -23.9\,ns) primarily due to deep combinational logic in the SFP row's absolute sum and division calculations. To achieve timing closure for a 1.0\,ns clock period, we added 3-stage pipeline in the accumulation and also add \texttt{-retime} to meet the timing requirement:
\begin{itemize}
    \item \textbf{Divider Optimization:}
    Previous synthesis timing reports indicate that the native Verilog / divider is the bottleneck of achieving 0 WNS. 
    Therefore, we implemented 2 possible upgrades of our division module. 
    \begin{enumerate}
    \item 6-stage pipelined long divider
    \item 10-cycle MCP native Verilog / divider
    \end{enumerate}
    Besides, the 2 designs share a common handshake interface with the core (\texttt{div\_start}, \texttt{div\_busy}, \texttt{div\_done}); macros (\texttt{SFP\_LONGDIV}, \texttt{SFP\_MCP}, \texttt{VANILLA}) are also defined to compile and synthesis the designs with ease.
    
    \textbf{Results.} 
    Both designs passed the Hold/Setup time check and the gate-level simulation. Nonetheless, we have to select the optimal design for PnR. Hence, we compare the synthesis result in Figure~\ref{fig:s5_divComparison}. 
    The 6-staged pipelined long division hardware outperforms the 10 cycle MCP Verilog / divider with ($\sim$23\%) lower area, slightly lower power, and much shorter synthesis time (10 min vs. 45 min).
    Thus, we select the pipelined long divider for PnR.
    \begin{figure}[htbp]
        \centerline{\includegraphics[width=0.30\textwidth]{Step5_images/Div_comparison.png}}
        \caption{Synthesis result of core with different division module}
        \label{fig:s5_divComparison}
    \end{figure}


    \item \textbf{Pipelining: Adder Tree Optimization:} The row energy accumulator was redesigned as a 3-stage pipelined reduction tree. After the 8 parallel multipliers, one pipeline stage captures the multiplication results, the next stage performs four pairwise additions, and the final stage reduces the partial sums to produce the accumulated row energy.


    \item \textbf{Chip Interface Design and Internal Control:} 
    The purpose of redesigning the chip interface is not only to remove redundant signals, but also to hide unnecessary internal details from the user. The interface should be intuitive and self-consistent, so that users can operate the chip without understanding internal dataflow or timing dependencies.
    Each core is independently controlled.
    We describe the interface usage from the perspective of a single core.
    \begin{figure}[htbp]
        \centerline{\includegraphics[width=0.30\textwidth]{Step5_images/Core_interface_redesign.png}}
        \caption{Core interface redesign}

    \textbf{Example Usage: MULT + NORM + READ.} 

    A user wants to compute matrix multiplication, apply normalization, save the result in KMEM for later use, but also want to read it out for verification.
    \begin{enumerate}
        \item Write data to KMEM and QMEM through \texttt{mem\_in} by designating \texttt{inst\_ext[5:0]}(SRAM operation \& addr).
        \item Set \texttt{mode\_in = 3'b001} (MULT+NORM $\rightarrow$ KMEM and PMEM) and assert \texttt{set\_mode} for one cycle to latch the configuration.
        \item Assert \texttt{start} for one cycle to begin execution. If the core is busy (\texttt{status[3]=1}), the \texttt{start} signal is ignored.
        \item During execution, \texttt{status[3]=1} indicates the core is busy, while \texttt{status[2:0]} indicate memory locks (QMEM / KMEM / PMEM).
        \item User may start to write K/QMEM data for next operation after the K/QMEM lock is freed.
        \item \texttt{status[3]} returns to 0 after the result is stored in PMEM and KMEM. The user can then issue PMEM read by designating \texttt{inst\_ext[5:0]}(SRAM operation \& addr) and wait for 1 cycle for the result at the \texttt{out} port.
    \end{enumerate}
    The above example involves external memory instructions and core mode setting. Refer to Figure~\ref{fig:s5_Controller_user_manual_spec} for details.

    \textbf{Design Insights.}
    \begin{enumerate}
        \item \textbf{Flexible data loading, fixed execution.} 
        The user has full freedom to write Q/K memory in any order and timing. 
        In contrast, execution follows a fixed address increment pattern, since the hardware performs a deterministic MAC sequence. 
        This cleanly separates user control from hardware scheduling.
        \item \textbf{Deterministic memory locking.} 
        After start, memories are locked and released in a fixed order. 
        Once a memory is released, it will not be locked again before the core becomes idle. 
        This gives a clear contract: unlocked memory is always safe to write.
        \item \textbf{Hardware-enforced protection.} 
        Although status signals are visible, correctness does not rely on the user. 
        Invalid operations (e.g., writing to locked memory or starting while busy) are automatically ignored by hardware.
        \item \textbf{Unified memory interface with minimal command set.} 
        All external memory accesses share the same interface (addr, data\_in, data\_out). 
        To avoid conflicts, only four commands are allowed: \texttt{NO\_OP}, \texttt{KMEM\_WRITE}, \texttt{QMEM\_WRITE}, \texttt{PMEM\_READ}.
        This eliminates read/write conflicts and simplifies controller design.
        \item \textbf{Mode-driven dataflow.} 
        A 3-bit mode encodes both operation type and result destination. 
        Results can be written to PMEM for output, or kept in KMEM for further computation. 
        This enables chaining operations without extra data movement.
        \item \textbf{Implicit pipeline support.} 
        The interface naturally allows overlapping computation and data loading. 
        While some memories are locked for computation, others can already be reused for the next stage.
        For example, in MULT+NORM mode, QMEM is released after MAC load, 
        so if user's next step is multiply norm by V, user can start writing V data while normalization is still running.
    \end{enumerate}

    \item \textbf{.mingu Shell (Matrix INstruction Generation Utility):} 
    The crown jewel of our verification framework is a custom, highly extensible simulation shell named the \textit{Matrix INstruction Generation Utility} (\texttt{.mingu}). Built on top of our Makefile flow and utilizing the hardware's unified interface, it completely abstracts away low-level testbench manipulation, allowing users to express verification tasks in a clean, scriptable format.

    The \texttt{.mingu} shell operates in a two-phase execution model:
    \begin{enumerate}
        \item \textbf{Configuration Phase (Before \texttt{fix\_set}):} Users define the environment using shell-level commands. This includes setting the simulation target (\texttt{set\_scope core|fullchip}), configuring the clock periods for asynchronous testing (\texttt{set\_clock\_period}), selecting the backend execution stage (\texttt{set\_sim\_stage sim|gls|post\_sim}), defining user variables (\texttt{set VAR value}), and controlling output features (\texttt{set\_dump\_vcd}).
        \item \textbf{Execution Phase (After \texttt{fix\_set}):} Once the environment is locked and compiled via \texttt{fix\_set}, the shell enters the interactive or batch testbench phase. Users issue high-level operations that perfectly map to our hardware's clean controller interface. Support includes data loading (\texttt{writeQ}, \texttt{writeK0}, \texttt{writeK1}), mode configuration (\texttt{set\_exec\_target}), operation triggers (\texttt{simulate}, \texttt{reset}), and automated golden model verification (\texttt{verifypmem}).
    \end{enumerate}

\subsection{Step 6: Sparsity-Aware Attention}
The final milestone validated the sparsity-aware feature. By injecting highly sparse matrices, we confirmed that the SFP engine correctly identifies rows below \texttt{SFP\_THRESHOLD} and outputs zeros, bypassing unnecessary long division cycles.

\textbf{Sparsity Definition and Threshold Calibration.}
We define the row-wise accumulation as:
\begin{equation}
S_i = \sum_{j} \left| (QK^T)_{i,j} \right|.
\end{equation}
A row is skipped if $S_i < T$, where $T$ corresponds to \texttt{SFP\_THRESHOLD}. To achieve a target sparsity of 30\%, $T$ is obtained from the empirical distribution of $S_i$ using Monte Carlo simulation over 10{,}000 datasets:
\begin{equation}
T = \text{Percentile}_{30}(S),
\end{equation}
ensuring approximately 30\% of rows satisfy $S_i < T$. The sparsity is defined as:
\begin{equation}
\text{sparsity} = \frac{1}{N} \sum_i \mathbf{1}(S_i < T).
\end{equation}

\textbf{RTL Skip Mechanism and Verification.}
In RTL, the accumulation from both cores is combined as \texttt{sum\_2core}, and the skip condition is evaluated via \texttt{sum\_2core < SFP\_THRESHOLD}. When triggered, the divisor is gated to zero (\texttt{sum\_2core\_gated}) and fed into the divider (e.g., \texttt{div\_longdiv}), allowing its FSM to bypass computation and force zero outputs without modifying the control flow. The same criterion is replicated in the testbench to count skipped rows and compute sparsity. Figure~\ref{fig:s6_layout} shows the corresponding layout.

\textbf{Results.}
Using 10{,}000 sample in \texttt{threshold.py} searching threshold, the threshold for sparsity we get is 169503. With this threhold, we test test with 1000 other random generated data ,and the measured sparsity we get is 34.975\%, close to the 30\% target. The deviation is attributed to distribution variance, demonstrating that the threshold generalizes well and that the RTL correctly implements sparsity-aware skipping. \section{Conclusion}
This project successfully demonstrates the design, implementation, and physical realization of a dual-core attention accelerator. By partitioning the system into asynchronous domains, we enabled flexible inter-core data exchange. Through the introduction of a Sparsity-Aware SFP engine, computations on insignificant data are bypassed, promoting energy efficiency. Most importantly, critical timing bottlenecks were identified and resolved via rigorous RTL repipelining, ensuring the design easily meets the 1.0\,ns clock constraint in a TSMC 65nm process. The progressive, step-by-step verification methodology guaranteed robustness from the behavioral level down to post-PnR gate-level simulations, confirming the design's readiness for physical fabrication.

\section{Mingu Shell Command Reference}
\label{sec:appendix_mingu}

The \texttt{.mingu} shell abstracts the complexity of cycle-accurate testbenches into a high-level scripting language. Below is the complete reference of supported commands, categorized by execution phase.

\subsection{Phase 1: Shell Configuration Commands}
These commands must be executed \textbf{before} \texttt{fix\_set}. They configure the underlying simulation backend, Makefile parameters, and output preferences.

\begin{itemize}
    \item \texttt{set\_scope <core|fullchip>}: Selects the hardware hierarchy to simulate. Determines whether to instantiate a single core or the dual-core fullchip.
    \item \texttt{set\_sim\_stage <sim|gls|post\_sim>}: Sets the simulation backend.
    \begin{itemize}
        \item \texttt{sim}: RTL behavioral simulation.
        \item \texttt{gls}: Gate-level simulation using synthesized netlist.
        \item \texttt{post\_sim}: Post-PnR gate-level simulation with delay annotations via \texttt{xrun}.
    \end{itemize}
    \item \texttt{set\_clock\_period <ns0> [ns1]}: Configures the half-cycle clock periods. If \texttt{ns1} is omitted, it defaults to \texttt{ns0} (lockstep). Example: \texttt{set\_clock\_period 1 1.2}.
    \item \texttt{set\_dump\_vcd <0|1>}: Toggles waveform dumping (\texttt{1} for ON, \texttt{0} for OFF). Disabling VCD significantly speeds up massive test runs.
    \item \texttt{set VAR value}: Defines a shell variable that can be substituted later using \texttt{\$(VAR)}. Example: \texttt{set PATTERN sw/pattern/random100}.
    \item \texttt{fix\_set}: \textbf{Required.} Locks all configurations, triggers compilation of the hardware design, and transitions the shell into the execution phase.
\end{itemize}

\subsection{Phase 2: Hardware Execution Commands}
These commands are executed \textbf{after} \texttt{fix\_set}. They map directly to the unified controller interface of the chip.

\begin{itemize}
    \item \texttt{set\_exec\_target <MODE>}: Sets the execution mode of the hardware controller (mapped to \texttt{mode\_in}).
    \begin{itemize}
        \item \texttt{CORE\_MODE\_MULT\_save\_to\_PMEM}: Standard $Q \times K^T$.
        \item \texttt{CORE\_MODE\_MULT\_NORM\_save\_to\_PMEM\_and\_KMEM}: Computes $Q \times K^T$, applies Softmax, and saves to both Partial-Sum memory and Key memory for subsequent computation.
    \end{itemize}
    \item \textbf{Memory Writers}: Loads text-based integer matrices into the internal SRAMs via the \texttt{inst\_ext} and \texttt{mem\_in} ports.
    \begin{itemize}
        \item \texttt{writeQ <filepath>}: Loads data into QMEM.
        \item \texttt{writeK0 <filepath>}: Loads data into Core 0's KMEM.
        \item \texttt{writeK1 <filepath>}: Loads data into Core 1's KMEM.
    \end{itemize}
    \item \texttt{simulate}: Asserts the \texttt{start} signal and waits until the core's \texttt{status[3]} (busy flag) goes low. Internally, the testbench computes the golden model equivalent for validation.
    \item \textbf{Golden Checkers}: Reads out the data from the PMEM via the \texttt{inst\_ext} port and compares it against the golden model.
    \begin{itemize}
        \item \texttt{verifypmem}: Checks PMEM results for all active cores and prints PASS/FAIL statistics.
        \item \texttt{verifypmem0 / verifypmem1}: Specific checks for Core 0 or Core 1.
    \end{itemize}
    \item \texttt{reset}: Asserts the hardware reset signal for two cycles, clearing internal states.
    \item \texttt{for <var> = <start> to <end> ... endfor}: Iterates block of execution commands. Variables inside the loop can be referenced using \texttt{\$(var)}. Nested loops are not supported.
    \item \texttt{exit}: Terminates the simulation gracefully and prints a summary of mismatches.
\end{itemize}
